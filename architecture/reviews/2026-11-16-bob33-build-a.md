## Migration 3 on the live data

- It is additive: two nullable columns (`outcome`, `outcome_reason`) with CHECKs that a null
  passes, and three new indexes whose names are unused (`schema.ts`). Existing rows keep null and
  read as unknown. Nothing is backfilled, as §3 says.
- `board.ts:22` runs the migrations inside `transactionSync`. If any statement fails, the whole
  migration rolls back and runs again on the next start. It can't leave half a migration behind.
- Building the indexes is cheap at BobNet's size: the board moved on 2026-11-15, so it has a few
  thousand events.

## Lost runs: tokens unknown, never 0

- The usage totals and `by_agent` leave out lost runs' tokens and count the runs in `lost` instead
  (`store.ts` usage loop). The dashboard shows "+ N unknown" and "N runs unknown", never 0, and
  says why ("Not counted as zero", `app.js` usage section).
- `done.sessions[].tokens` adds lost runs' zeros, and `lost` comes with it. The page shows
  "+ N runs unknown" next to the session. That is the ADR's shape, so it's fine.
- **Finding 1 (major, BOB-42).** `heavy` compares `tokensOf(s)`, the sum of all the session's runs
  including a lost run's zeros. It also builds a kind's `usual` median from sessions that may have
  lost runs. So a lost run counts as 0 there in two ways: a session with a lost run looks cheaper
  than it was, and it pulls its kind's median down, which makes other sessions look heavy. Ruling
  (ADR 0005 §2, amended): a session with `lost > 0` is never judged heavy, and it is left out of
  every comparison set, including the count toward the 5-session minimum. Criterion: a test in
  `board-status.test.ts` shows both. I couldn't create BOB-33 tasks (Peach's grant), so I captured
  it as BOB-42 for Peach to slot under BOB-33.

## Version skew and rollout

- **Old supervisor, new broker.** `outcome` and `reason` are optional (`board.ts` `run_end`). An
  rc.36 `run_end` stores null for both and reads as unknown. A run with no outcome is never listed
  as stuck (tested). Old supervisors don't sweep, so runs left open by restarts stay open, as §3
  says.
- **New supervisor, old broker.** An old broker strips the optional fields. A sweep's `lost` would
  then be stored with no outcome and zero tokens, and later read as a run that used no tokens.
  That's why the broker goes first: the order protects the data, it isn't a safety rule. §6 now
  says this.
- **The sweep** (`supervisor.ts:269-279`) covers only workers in `running` or `waiting-*`, which
  all sent `run_start` earlier through the same ordered outbox. It skips roles that are no longer
  configured (`roleOf` would throw), and `boardReport` skips projects that aren't on the service.
  If the board refuses a report, the outbox logs it and drops it, so it can't block the queue.
  `run_end` on a run that has already ended is a no-op. Normal exits cut the reason to 300
  characters, matching `RUN_REASON_MAX` and the column's CHECK.
- The export gains optional `outcome` and `outcome_reason`, and import restores them. A version 1
  file from before still parses.

## Cost

- The scale test (`board-scale.test.ts`) took 32 ms for a week across two Helix-sized projects with
  a month of work. I also ran two variants and deleted them afterwards: the full 31-day span took
  100 ms, and 94 ms with 400 context points on every run. (The read does `SELECT *` on runs, ctx
  blob included. The cost is negligible at these sizes.) Everything is under 250 ms.
- **Finding 2 (minor, BOB-43).** *answered and still holding* walks every answered question with
  holds the project ever had, with three or four queries each. The span doesn't bound that walk,
  and the scale test has no questions. Add them to the test, and bound the walk if it shows. The
  cost note in §2 says this.

## Luigi's open questions, settled in ADR 0005 §2

- **`more`**: one map on the row, list path → how many were left out, present only for a list that
  was cut. `done.counts` stay whole numbers.
- **`since`**: clamped to at most 31 days back and to no later than now.
- **`by_agent[].role`**: the role of the agent's latest run in the span.
- **Bugs in `done.features`**: yes, a bug of any kind (task or backlog item) counts, in the list and
  in `counts.features`. `type` tells the two apart.
- **`sessions_estimate`**: the last 20 Done features that had at least one session, ordered by their
  last move to Done. Features imported Done with no sessions would pull the median to 0.
