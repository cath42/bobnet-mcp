## Verdict

**Sound in shape; fix seven majors before acceptance.** It keeps message ops, makes the supervisor
the requester, keeps the target as the authority, and adds no land lease. All four are right, and
each is well argued from the code. The loop guard (§2) is correct against today's code (old replies
carry `op` and `in_reply_to`; `readRequest` returns null without `op`, remote.ts:44). §9's
mixed-version refusals hold. §10 follows from ADR 0002 §4.6/§5. Criterion 6's re-check of the config
at answer time is right. The majors all sit where the durable path and the request lifecycle meet
the broker's actual behaviour. None of them changes the shape. 0 blockers, 7 majors, 9 minors.

## Majors

**M1. The outbox, as specified ("as `notify` does"), can't carry replies or events.**
`flushMessages` prefixes every body with `(sent …) ` (supervisor.ts:1667), so the JSON no longer
starts with `{` and is never read (remote.ts:40). It sends without `in_reply_to`. It also stops at
the first failure (:1670-1672), so one body the broker refuses for good blocks every later outbox
message, `notify` to poe included, forever. Refusals that last are `secret_detected`,
`unknown_message`, `unknown_peer` and too long.
*Fix:* add an outbox kind `remote` that stores to, the body verbatim, `in_reply_to` and ttl. Flush it
in order. Drop final errors with an audit row; transient ones wait. Say this in §2.

**M2. Replies depend on the request message still existing.** The broker refuses `in_reply_to` for
a message it no longer has (`messageExists`, broker.ts:296-298). Requests carry a ttl of 20-30 s,
and the hourly sweep deletes expired messages (broker.ts:35, 741-742). Two cases lose their reply to
`unknown_message`:
- a spawn reply after a board `session_join`, which can take up to 60 s (supervisor.ts:394-407),
  whenever a sweep falls in between;
- any reply held in the outbox past a sweep, which with M1 unfixed then blocks the queue.

*Fix:* put the request's message id in the reply body (`re_id`) and match on that. Treat
`in_reply_to` as a hint, and on `unknown_message` resend without it.

**M3. A spawn is not idempotent, and "never queued" is not atomic.**
- (a) Today a request is deduplicated only once its reply is recorded (supervisor.ts:771, 781), and
  the ack comes after the work (:726). A reconnect within the ttl during a slow spawn redelivers the
  message (`pendingFor`, broker.ts:276-277), and a second worker starts.
- (b) §3 checks `queuedBecause` before an async `session_join`. In that gap another spawn can take
  the role or the laptop's limit, and the "refused" v:2 spawn queues after all. A refusal after the
  join leaves a board session joined with no worker.
- (c) After "may or may not have run", poe's natural retry is a new message.

*Fix:*
- Record the message id as in progress before doing any work.
- Run the refusal check again synchronously in `spawn()`, just before the row is made, and handle a
  refusal after the join (leave the session, or say it dangles).
- Give `spawn` a requester-chosen `key` that the target deduplicates for a day, so a retry returns
  the first result.
- When the tool times out, the requester runs `list` itself before saying "may or may not".

**M4. Late replies and events are dropped on the requester.** §2 says unmatched replies are
"logged and dropped". §7 accepts events only "for a worker this supervisor spawned there". The
requester learns a worker id only from the spawn reply, and its waiters are in memory. If the tool
timed out, or the requester restarted while waiting, the reply matches nothing. Every later event
for that worker is then dropped, and a live remote worker becomes invisible and unanswerable. That
breaks §3's "spawned after all".
*Fix:* persist each sent request (message id or `key`, op, laptop, sent_at) in SQLite before sending.
When a spawn reply arrives, at any time, it creates the copy. An event from the right target for an
unknown worker it says this supervisor spawned creates a copy (the target owns the truth, §7) rather
than being dropped.

**M5. A target restart tells nobody who needs to know.** On start, the target fails its running
workers without an `exit` event (supervisor.ts:269-280; `remoteEvent` is called only at :970 and
:1506). It tells only its own orchestrator (`notify`, :308-314), the poe@ubu1 that Casper means to
retire. §8 ("orphaned requests are §4's") then depends on §7's reconcile. That reconcile runs only on
a presence `joined`, which is team-filtered (ADR 0004 §5) and missed when the requester was offline
itself.
*Fix:*
- On start, the target sends each remote spawner, durably, an `exit` (failed: supervisor restarted)
  per lost worker, and a new `orphaned` event per open request (add `orphaned` to §2's events).
- The requester also reconciles on its own start and connect, and whenever it first sees the target
  online in the peer list.

**M6. A remote worker's own messages go to the wrong laptop.** Bare names resolve to the sender's
laptop (address.ts:30-36). A worker on ubu1 that writes to "poe" (or to a lead or Mario by name)
reaches poe@ubu1 instead. That peer is either queued for a retired session (peers are kept 30 days,
broker.ts:38) or is "No such peer". Supervisor notices are fine, because they go as events; the
worker's own `send_message` is not.
*Fix:* the target tells a remote-spawned worker its orchestrator's full address
(`remote_by`@requester's laptop) in the brief preamble or the worker's MCP instructions. The ADR
should say remote briefs use full addresses. Optionally, the worker's `send_message` could map the
bare orchestrator name to the spawner. Add this to §11's assumption.

**M7. More crosses the broker, and stays there for 30 days.** ADR 0004 §4 counts "a broker whose
storage or traffic is read" among its threats. 0007 sends these through the broker:
- full tool inputs (the `request` op);
- transcript tails;
- previews;
- handoff text.

Replies and events get no ttl, so the default of 30 days applies (`LIMITS.defaultMessageTtlSeconds`,
frames.ts). `findSecret` is a heuristic.
*Fix:*
- Give every reply and event a ttl: a reply's ttl is the requester's wait plus a margin; an event's
  is the reconcile window, e.g. 7 days.
- Cut `request` and `tail` to what poe needs to decide.
- Record the widening in Consequences and against ADR 0004 §4.

## Minors

- **m1. The answer grant includes the human tier; make that explicit.** Locally, `user_decided` is
  asserted by the caller (mcp.ts `answer_request`: `x.user_decided ? "human" : "orchestrator"`). A
  `remote` entry for `supervisor@mbp-1` therefore hands ubu1's human-tier decisions to anything on
  mbp-1 that holds the MCP token, unsandboxed workers included. Also, `spawned_by` is the
  supervisor, so any orchestrator on mbp-1 can answer or stop another orchestrator's remote workers.
  Both are consistent with ADR 0004 §4 and Q-6, but Casper should accept them knowingly. *Fix:* one
  line in §4 and in the `remote` config comment (config.ts:214-218).
- **m2. Size the serialized body, not the handoff.** The 16 Ki limit (`bodyChars`) applies to the
  whole JSON. Escaping, the checkpoint, the error and the land outcomes come on top of 12,000
  characters, and the error and land outcomes are unbounded. *Fix:* cut the handoff until
  `JSON.stringify(body).length` fits, with a margin.
- **m3. A withheld handoff leaves nothing.** If the handoff trips `findSecret`, poe gets no result
  and the role has already ended. *Fix:* say what poe does (spawn the role on the target to
  summarise it), and test that the resend drops only that field.
- **m4. Target address.** Don't assume `<own name>@laptop`. *Fix:* use the laptop's reporter as the
  broker pins it (broker.ts:266, `laptop_reports.reporter`), or the peer list.
- **m5. Rollback.** A target downgraded below rc.N sends v-less events (`{event, worker}`) and
  announces requests to its local orchestrator. *Fix:* the requester accepts v-less `exit` and
  `remote_control` from a target it spawned on, and §9 states the downgrade behaviour.
- **m6. Rollout restart.** Restarting a supervisor fails its running workers (supervisor.ts:269).
  *Fix:* §9 says to restart when `list_workers` is empty.
- **m7. §10's trigger can't be measured as written.** The `land:stale` audit doesn't know the
  winner's laptop. *Fix:* name the source: the board's push records (ADR 0004 §1) or the commit's
  author mapped to a laptop.
- **m8. Spike 9 (clocks) is mostly moot.** Expiry and `created_at` use the broker's clock, and the
  requester's deadlines are local durations; only `as_of` display depends on skew. *Fix:* narrow it
  or drop it.
- **m9. The spike misses the cases that bite.** *Fix:* add:
  - a reply sent after the request has expired and been swept (M2);
  - a redelivery during a slow spawn (M3);
  - a broker outage with queued events (M1);
  - a target restart with a remote worker running (M5);
  - a remote worker writing to "poe" by bare name (M6).

  Each can be shown on today's code with hand-written JSON.

## Simpler alternatives worth pricing

- **Point the target's orchestrator at the one poe.** On ubu1, set
  `orchestrator: poe@mbp-1` (per project, or for the laptop); `notify` already accepts a full
  address. Every notice from ubu1 would then reach the one poe with no new event routing: requests,
  ends, restart notices, and workers ubu1 spawned locally. That covers M5, and the "one answerer"
  split of §4 goes away. This is Casper's end state anyway, since poe@ubu1 is retired. It doesn't
  replace the tools, the `answer` op or the copies. It could replace the `request`, `settled` and
  `exit` routing by `spawned_by`, at the cost of notices arriving as text rather than structured
  copies. My recommendation is to keep the ADR's structured copies and adopt this for the restart
  notice and for workers spawned locally on ubu1.
- **Stage the ops.** Do `spawn`, `status`, `stop`, `list`, `answer` and `exit` with the handoff first
  (criteria 1-6), and `tail`, `request` (full input) and `slots` later. That lowers M7's surface and
  the build size.
