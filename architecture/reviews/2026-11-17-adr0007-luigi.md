# Review: ADR 0007 (one orchestrator across laptops), as its builder

- **Reviewer:** Luigi, 2026-11-17, session `BOB-44 design A`, step 4 of `lead/bob44/design-session.md`.
- **Read:** ADR 0007 at v2 `e918fa3`, against the code at the same commit: `packages/supervisor`
  (`remote.ts`, `supervisor.ts`, `router.ts`, `mcp.ts`, `lead-tools.ts`, `store.ts`, `test/fakes.ts`,
  `test/remote.test.ts`), `packages/protocol` (`frames.ts`, `secrets.ts`, `board.ts`) and the broker's
  message path (`packages/broker/src/broker.ts`, `board/rules.ts`, `vitest.config.ts`). Criteria:
  `product/requirements/remote-orchestration.md`.
- **Verdict:** buildable, and the shape is right (messages, not a frame; the supervisor as requester;
  the target the only authority). It is not buildable *as written* in two places: the outbox it leans
  on can't carry the events (1), and its replies can be refused by the broker (2). Seven majors are
  gaps the build would otherwise discover in review. With the fixes, about 11 engineer-days (cost table
  at the end), which fits two builds of ≤ 7 tasks.

## Findings

### 1. Blocker: the outbox can't carry events or replies

§2 says events and replies "go through the outbox (`store.addOutbox`, as `notify` does)". The outbox
breaks all three things §2 needs from it:

- **It changes the body.** `flushMessages` sends `(sent ${created_at}) ${body}` (`supervisor.ts:1667`).
  A JSON body becomes text that doesn't start with `{`, so the receiver's `readRequest` returns null
  (`remote.ts:41`) and the receiver only logs it. Every event the outbox delivers is lost.
- **It drops `in_reply_to` and `ttl_seconds`.** The `outbox` table has `to_name, body, created_at,
  kind` (`store.ts:95-110,290`). A reply that waited in the outbox goes out as an unanswered message.
- **It doesn't keep order.** `notify` sends directly and falls back to the outbox only when the send
  fails (`supervisor.ts:1601-1606`). A later send that works overtakes an earlier one still waiting.
  The `settled` before `request` case is finding 5.
- **One final error stops it for good.** `flushMessages` stops at the first failed send
  (`supervisor.ts:1665-1673`) and retries the same row each flush. A row the broker will never take
  (`secret_detected`, `unknown_peer`, `unknown_message`, `bad_frame`) holds up every row behind it,
  `notify`'s included. That is a bug today; remote traffic would make it likely.

**Fix:** add an outbox kind `remote` with columns `in_reply_to` and `ttl_seconds`, sent verbatim (no
prefix). Every remote reply and event is enqueued first and then flushed, never sent directly, so order
is the outbox's `seq`. Treat the broker's final codes as final, as `flushBoardReports` already does
(`supervisor.ts:1685-1706`): log the row, audit it (`remote:undeliverable`) and drop it. Apply the same
final-code rule to kind `message`. Test: broker down, three events queued, broker back, all three
arrive in order and parse.

### 2. Major: a late reply is refused by the broker

`sendMessage` refuses a send whose `in_reply_to` names a message the broker no longer holds
(`broker.ts:302-304`, `unknown_message`). The ADR gives requests a TTL of 20-30 s (§2). An expired
message is deleted at the next hourly sweep (`broker.ts:35,739-742`). So a reply sent after the
request expired is refused whenever a sweep fell in between. That covers:

- a `spawn` whose board join takes up to 60 s (§2 itself allows 90 s);
- a reply that waited in the outbox through a broker outage (finding 1);
- a reply after the target reconnected and handled a redelivered request.

The failure is silent: `toRemote` only logs (`supervisor.ts:846`). poe gets "may or may not have
run", and with finding 4 it never learns of the worker. It happens rarely, at random, and only in the
field, which is the worst kind of bug to find later.

**Fix (no broker change):** every v: 2 reply carries the request's message id in its body
(`req: "<message id>"`) and is matched on that, never on the envelope. Send it with `in_reply_to` as
the dashboard's thread hint; on `unknown_message`, resend it once without `in_reply_to`. §2's rule
for what counts as a request already doesn't depend on `in_reply_to` alone (`re` marks a reply), so
the resent reply is still never answered. Test with the network fake (finding 11): sweep between the
request and the reply.

### 3. Major: a redelivery during a spawn runs it twice

The supervisor acks a message to itself only after `onRemote` finishes (`supervisor.ts:726`). A
`spawn` takes up to 60 s (board join, `:394-407`). `remoteReply` is written only after `remoteDo`
returns (`:782`). If the WebSocket reconnects in that window, the broker redelivers the unacked
message while it is unexpired (`pendingFor`, `broker.ts:617-627`). The second `onRemote` finds no
reply, so it spawns again. Today that queues a second worker. Under v: 2 it is refused as "already has
a worker running", and the requester gets two replies to one request, which may arrive in either
order. This is a bug today; the 60 s join makes the window real.

**Fix:** before `remoteDo`, insert the `remote_requests` row with `reply` null (in progress). A
redelivery that finds the row in progress is acked and ignored, and the first run's reply is the only
one sent. Make `remoteReply` return `"pending"` for that case. Cost: an hour, with a test.

### 4. Major: events for a worker the requester doesn't know are dropped

§7 accepts an event "only for a worker this supervisor spawned there". The requester learns the
worker's id only from the `spawn` reply. That reply can be lost (finding 2), arrive after the 90 s wait
(the tool has already said "may or may not have run"), or be overtaken by an event (finding 5). In each
case the worker runs on ubu1, its `request` events are dropped as unknown, poe is never asked, and the
target's timeout denies every request.

**Fix:**
- Accept a v: 2 event from the target supervisor (`<name>@<laptop>`, §7's sender check) for an
  unknown worker. The target sends events only for workers whose `spawned_by` is this supervisor, so
  the sender check is the authority. Create the copy on first sight and ask `status` to fill it.
- Every v: 2 reply and event names the spawn request it stems from (`spawn_req`, the message id
  stored with the worker on the target). The requester can then tie a late worker to the spawn poe was
  told about ("spawned after all", §3).

### 5. Major: no ordering guarantee between events

The ADR assumes events arrive in order and never says why. Three things can reorder them:

- direct sends overtaking outboxed ones (finding 1);
- `onRemote` being async (`void this.onRemote(msg)`, `supervisor.ts:726`), so the requester's
  handling of two events can interleave if either awaits;
- after an outage, the broker's pending delivery is ordered by `created_at, id`
  (`broker.ts:620-624`), which is send order only within one connection.

If `settled` lands before `request`, the copy stays open for good: `pending_requests` shows a request
the target closed, and `answer_request` gets "already answered".

**Fix:** finding 1's always-enqueue rule gives send order. On top of it, each event carries a
per-worker `seq` from the target (a column on the worker row). The requester applies an event only if
its `seq` is above the copy's last, and handles remote messages synchronously (no `await` between
reading and writing a copy). A `request` event for a request whose copy is already settled is
ignored.

### 6. Major: reconciling misses the requester's own restart, other teams, and old workers

§8 says the requester reconciles when it is back, but §7 reconciles only on the target's presence
`joined`. When mbp-1's supervisor restarts, ubu1 is already online, so no `joined` comes. A connection
also hears another peer's presence only if it hosts a peer with no team or on that peer's team
(`broker.ts:676-690`). Two supervisors with different `team` settings never hear each other. And
`list` returns the last 20 of the sender's workers (`supervisor.ts:819`): a live worker older than 20
spawns is missing from it, so §7 marks it `unknown`.

**Fix:**
- Reconcile on the requester's start and on every `onConnected`, on `joined`, and on a timer
  (every 5 minutes) while any copy is not ended.
- v: 2 `list` takes `ids` (the requester's copies that are not ended) and returns those workers with
  their open and orphaned requests.
- Mark `unknown` only an id that was asked for and not returned.

### 7. Major: the target still tells its own orchestrator about v: 2 workers

§4 reroutes `announce`, but three other target notices about a remote worker still go to the
target's orchestrator through `notify`:

- the end notice (`supervisor.ts:1520`);
- Remote Control failing (`:973`);
- the restart notice, which lists "Requests still answerable" (`:309-314`).

While poe@ubu1 lives, that last one invites it to answer requests §4's one-answerer rule refuses it.
Once poe@ubu1 is retired, these notices sit at the broker for 30 days (`frames.ts:30`).

Separately, workers orphaned by a target restart (`:269-283`) get no `remoteEvent`, so the requester
never gets their `exit`, and the handoff the worker may have written never reaches poe (criterion 5).

**Fix:** for a v: 2 worker, each of these notices becomes an event to the spawner and none goes to the
target's orchestrator. At start, the target sends `exit` (state `failed`, "supervisor restarted", the
handoff text if the file exists) for each v: 2 worker it orphans. It sends `settled` with state
`orphaned` for each of their open requests, so the copy shows "answering resumes the worker". All of
these go through the outbox, which flushes when the target connects.

### 8. Major: `settled` has six sources; the ADR names three

A request's state changes in six places:

- `router.answer` (`router.ts:126`);
- the timeout (`router.ts:171`);
- the dismiss path (`supervisor.ts:566`);
- `expireOrphans` (`supervisor.ts:606`);
- `markOrphaned` at start (`:282`);
- the abort path, when the worker stops while waiting (`router.ts:190-199`). Nothing settles the
  store's row there: it stays `open` until the next restart orphans it.

Emitting `settled` at each site by hand will miss one, and a missed one is a copy open for good.

**Fix:** one choke point. The supervisor wraps `store.settleRequest` and `store.markOrphaned` with a
hook that emits `settled` for v: 2 workers' requests. The abort path settles its row (state
`expired`, decided by `stop`) so the copy closes. Test each of the six paths.

### 9. Major: refused credentials should be checked before sending, not after

§2 waits for the broker's `secret_detected` and then "resends without the field". With finding 1 that
refused row blocks the outbox. Without it, it is still a round trip per event. And withholding the
whole handoff loses criterion 5's text over one token-shaped string. The broker's check is
`findSecret` from `@bobnet/protocol` (`protocol/src/secrets.ts:17`), which the supervisor already
depends on.

**Fix:** the target runs `findSecret` on each field before enqueueing. It replaces the matching span
with `[withheld: looks like a credential]`, so the rest of a preview or handoff still goes. If the
broker refuses anyway (a version skew in the detector), that is a final code (finding 1): the event is
dropped and audited, and the target sends a short `withheld` event in its place.

### 10. Major: the requester has no record of what it sent

The Consequences give the requester two tables (remote workers, remote requests). Matching a reply to
"what it sent" (§2), "spawned after all" (§3), and a reply that arrives after the requester restarted
all need a third: one row per op sent (message id, laptop, op, the worker or request id, deadline,
outcome). Keeping it in memory loses every reply that lands after a restart. The name "remote requests"
also collides with the target's existing `remote_requests` table (`store.ts:102`, the inbound dedupe).

**Fix:** three requester tables:
- `remote_workers`: copies of the workers this supervisor spawned elsewhere;
- `remote_asks`: copies of those workers' permission requests and questions;
- `remote_sent`: one row per op this supervisor sent.

Say so in the Consequences.

### 11. Major: the test the ADR relies on can't run with today's harness

The Consequences and §2 cite "a test of two supervisors on one broker". There is no such harness:

- `FakeBroker` (`test/fakes.ts:154-205`) is one laptop. `register` always answers `@mbp-1`, `send`
  records and reports everything as delivered, and nothing routes from one instance to another. It has
  no TTL, queue, ack or redelivery, presence, `in_reply_to` check or secret refusal.
- The real broker's tests run inside workerd (`broker/vitest.config.ts`, miniflare). The supervisor
  (node:sqlite, child processes, the filesystem) can't run there.

**Fix, two parts:**
- `FakeNetwork` in `supervisor/test`: several laptops, each supervisor given its own link. It routes by
  `name@laptop`, reports `delivered_to` and `queued_for`, keeps undelivered messages until TTL, applies
  the `in_reply_to` check with a test-controlled sweep, redelivers unacked messages on reconnect, emits
  presence `joined`/`left` with the team rule, and refuses on `findSecret`. Each of findings 1-8 gets a
  test there, plus the loop test §2 asks for.
- Broker e2e tests (`broker/test/e2e.test.ts`) that pin the four behaviours the fake copies: an
  undelivered message expires; `delivered_to`/`queued_for`; `in_reply_to` to a swept message is
  refused; pending messages are delivered in order.

Cost about 1.5 days, and it has to come first in build A.

### 12. Minor: "offline" can look online

`online` means the Durable Object still has the socket (`broker.ts:670,698`). A laptop that went to
sleep can keep a half-open socket for a while, so `delivered_to` names it and the 30 s request
expires undelivered. The tool's "may or may not have run" covers the outcome. **Fix:** say so in §3
rather than claiming the refusal is always immediate, and add to the spike (§"Spike to confirm", 2):
how long a sleeping ubu1 still shows online.

### 13. Minor: size the exit event on the whole body

§6 caps the handoff at 12,000 characters, but the 16 KiB limit (`frames.ts:25`) applies to the
serialised body. JSON escaping, the checkpoint (≤ 300), the land outcomes and a failed run's `error`
(no length limit, `supervisor.ts:1506`) all add to it. **Fix:** cut the error to 500 characters, then
cut the handoff to whatever the body has left after everything else is serialised. Keep
`handoff_truncated` and the file's length. Test with a 16 KiB handoff full of quotes and newlines.

### 14. Minor: make `by` required, and carry it into a resumed worker

§4's routing and §7's `remote_by` both need the target to know a worker came from a v: 2 spawn. The
ADR stores `by` "for the audit and the dashboard". **Fix:** `by` is required in a v: 2 `spawn`. A
non-null `remote_by` on the worker row is what marks it as v: 2, so routing has one test rather than
two columns. `answer`'s resume path (`supervisor.ts:576-588`) passes `spawnedBy` but would drop `by`;
it must copy both.

### 15. Minor: comparing rc versions needs code

§9 compares `2.0.0-rc.37` with the version required. There is no semver code in the repo. **Fix:** a
small `x.y.z[-rc.n]` comparison in `protocol`. An unparseable or missing version is sent anyway,
relying on the old target's bad-request reply, which §9 already names as the fallback and which
holds (see "Checked").

### 16. Minor: v: 2 `as: "lead"`

Today's `spawn` accepts `as: "lead"` (`remote.ts:24`). A remote lead spawns its own workers on the
target. Their `spawned_by` is the lead's id, not the requester, so their requests are announced on the
target, outside §4. The ADR doesn't say whether that is intended. **Fix:** refuse `as: "lead"` in a
v: 2 spawn for this version (keeping one answerer simple), listed in §11.

### 17. Minor: the lead's view and `laptop: "all"`

- §5's `pending_requests` is "always local and remote together", but `handlers(sup, { lead })`
  (`mcp.ts:162`) serves a lead with the same function. **Fix:** remote rows and remote ids are only
  for the non-lead caller. A lead's `answer_request` with a remote request id is refused like
  `laptop`.
- `laptop: "all"` is also a valid laptop name (`frames.ts:35`). **Fix:** use `"*"`.

### 18. Minor: wording

- The status line and "Spike to confirm" cite "§13", which doesn't exist (the spike section has no
  number). Number it §12, or cite it by name.
- §8: "its notices to poe wait in the outbox and go when poe is back (`supervisor.ts:716`)". `notify`
  hands them to the broker, which queues them for an offline poe for 30 days. The outbox holds only what
  the broker didn't take because it was down.
- `remote.ts:4-9` and `config.ts:214-218` also say the requester is "another laptop's orchestrator".
  Under v: 2 it is the supervisor; update that wording with "answers no request".
