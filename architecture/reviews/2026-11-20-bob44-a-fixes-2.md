## How I checked

I ran `secrets.ts` at dd9279e with node 24 (scripts outside the repo):
- **The ruling's lists:** every "must match" matches, and every "must not match" doesn't. That includes the
  stand-in texts, the broker's and the client's `secret_detected` messages, `PGP PUBLIC KEY BLOCK`,
  `CERTIFICATE`, and PuTTY's header without its colon.
- **Redaction then `findSecret`:** null for every case. The cases were the corpus, a nested PEM, a stray END
  before a key, an unclosed BEGIN in prose, PGP with CRLF, a v3 `.ppk`, and `api_key = sk-ant-…` (one mark).
- **A fuzz of 200,000 random strings over the patterns' alphabet** (keywords, `_`, `=`, `:`, whitespace, `\`,
  quotes, BEGIN, the PuTTY header, U+2028, non-ASCII): no string's serialised form matches where the string
  doesn't. So §2's property still holds for one field. Across fields it is BOB-81's re-check.
- **200 KB adversarial inputs:** `_password` repeated, BEGIN or END lines, `.ppk` headers, `Private-MAC: `
  repeated, a 39-letter label repeated, and BEGIN/END pairs. Each takes under 6 ms for `findSecret`, for
  redaction, and for `findSecret` on the serialised text. That is well under the 50 ms bound.

## Findings

**1 (minor): `remote_workers.state_withheld` never goes back to 0** (`supervisor.ts:1252`, `:1178`). This is
Mario's candidate, and I confirm it.
- Once the orchestrator has been told (state 2), `copyView` carries the 2 forward through every view that
  passes. A later withheld event on the same copy then asks no `status` and sends no notice.
- If reconcile's `list` passes, the copy still ends within `RECONCILE_MS` (5 min), so in that case it is only
  a delay. If the `list` is withheld too, the copy stays `running` and the orchestrator isn't told again.
- That takes two separate episodes of detector drift on one copy. After BOB-80's deploy there is no drift
  unless a laptop is rolled back.
- **Fix (Luigi, backlog):** set `state_withheld: 0` in `copyView` when a view passes, and on an event that
  passes. Notices are then bounded at one per withheld episode, and each episode needs a passing view in
  between. My §14 line "BOB-78 bounds it to one notice per copy" becomes "one per episode". I've noted that
  in the ADR's "As built" paragraph.

**2 (minor): a `summary` reply can now go out both `ok: true` and `event: "withheld"`** (`:1692`, `:1097`,
`:1109`).
- Since BOB-81, `withHandoff` can return the stand-in. The `summary` case strips `v`, `re`, `req` and `ok`
  from it, and the handler wraps the remainder as an ok reply. On the wire that is
  `{v:2, re:"summary", req, ok:true, event:"withheld", worker:"<id>"}`.
- The requester handles it correctly. `classifyRemote` reads it as an event with `req`, so it is checked
  against `RemoteWithheld`, which is loose, so the extra `ok` passes. `copyFromReply` then calls
  `summaryWithheld`, and `worker` is a string, so `copyView` is skipped.
- But §2 defines no "ok and withheld" shape. A tool waiting on the reply sees `ok: true` with no view.
- The audit records `remote:summary` with a null worker (`:1111`), where it should be a withheld.
- It needs a cross-field match in a summary, which no current reply has.
- **Fix:** when `fitted.event === "withheld"`, send the stand-in as the reply, without `ok`, as
  `withholdBody` does for every other op.

**3 (minor, note): while one copy's `list` stays withheld, each reconcile pass logs a warning and writes
one `remote:list_withheld` audit row** (`:1389-1392`). That is one row per laptop every 5 minutes for as
long as the drift lasts. This is "reported once" per pass as BOB-78 asked, and the drift heals. No fix
unless the audit grows in practice. A fix would be to report only when the withheld set changes.

## Rulings checked

**BOB-80, `findSecret` as ruled (`secrets.ts:9-36`).**
- `password_assignment`: the pattern is the ruled one exactly, split into `ASSIGNMENT` + `ASSIGNMENT_VALUE`
  so that redaction can take a marked value (`:103`). The `(?!_detected\b)` guard is applied case-insensitively
  under `/i`, so `SECRET_DETECTED: …` isn't detected either. That is harmless.
- `private_key`: the ruled pattern, under `/i`. `putty_key`: the ruled header (case-sensitive) and the ruled
  END (any case). Its END is the end of the Private-MAC's hex, not of the line. That is equivalent, because
  the hex runs to the line's end in a real `.ppk`.
- The name `putty_key` appears only in the broker's error text (`broker.ts:637`) and the client's close error
  (`board-tools.ts:173`). Nothing branches on it, so the name is additive.
- The redaction order: blocks first, then the token patterns, then `password_assignment` last. That gives
  `DB_[mark]` and keeps `DB_`, as ruled.

**BOB-79, linear pairing (`secrets.ts:51-82`): as ruled in §14 point 4.**
- Each kind's BEGINs and ENDs are found once (`matchAll`). The walk is a stack, so an END closes the latest
  open BEGIN. A nested key goes with its outer one, and a stray END is left alone.
- An unclosed BEGIN redacts to the end of its line (`\r` or `\n`). The remaining open starts stay in
  ascending order, so the end-of-line scans don't overlap, and the whole pass is linear.
- A BEGIN quoted in prose before a real key stays its own line, and the key is redacted whole. I ran that
  case.

**BOB-81 (`supervisor.ts:197-224`, `store.ts:223`).**
- The re-check after `withholdWhole` sends `standIn(out)`, with `re`/`req` for a reply and
  `worker`/`spawn_req` for an event. That is the same shape as the broker-refusal stand-in (`withheldBody`
  now shares `standIn`), so the requester can't tell the two apart and needs no change.
- `withHandoff` returns the stand-in as it is (`:303`). Finding 2 is the one caller that rewraps it.
- `DatabaseSync.isTransaction` exists in `node:sqlite` on Node 24. I checked it: false, then true after
  `BEGIN IMMEDIATE`, then false after `ROLLBACK`. The guard rethrows the real error, as I asked in my review
  of A-fixes, finding 2, and the test simulates SQLite's own rollback.

**BOB-78, requester side: my advisory (c)(b), as built.**
- A withheld `list` batch no longer ends the pass (`:1386`). It is reported once at the end. A missing reply
  or an `ok: false` still stops the pass, as AC 5 asks.
- A withheld event sets 1 and asks `status` (`:1178-1183`). A copy first made from a withheld event starts
  at 1 (`:1173`). A withheld `status` at 1 sets 2 and tells the orchestrator once (`:1274-1281`). Nothing
  asks it `status` again, and a passing `list` or the real `exit` still ends it.
- No loops. The only path that asks for more is a withheld event, and that asks for at most one `status`.

**The store: the `state_withheld` column (`store.ts:116`, `:206-207`, `:490-495`).**
- It is an additive `ALTER TABLE … ADD COLUMN … NOT NULL DEFAULT 0`, guarded by `table_info`. Fresh dbs
  get it from the `CREATE`. It is the supervisor's local SQLite, so it needs no broker migration.
- A rollback to rc.41 is safe: its `INSERT` names its columns, so the new one takes its default, and its
  `SELECT *` carries an extra field that nothing reads.
- `putRemoteCopy` takes the whole row, so the type makes every caller pass `state_withheld`. The three
  callers do (`:1174`, `:1181`, `:1252`).

**`lead/bob44/a-fixes.md`: the corrected known limit is accurate.** It is BOB-78 AC4's repo half. The rc.42
notes are the other half.

## Not ruled here (for Peach and Casper, older than this range)

The broker checks the raw body, and in a JSON body a line's start is escaped as `\n`, `\t` or `\r`. So
`password=…` at the start of a line inside a JSON body isn't caught there: the `n` before the keyword fails
the lookbehind, as it failed `\b` before. The target redacts each field first, so supervisor traffic is
covered. Only a hand-written JSON body from an agent isn't. This gap is older than BOB-80, which neither
widens nor narrows it, and closing it needs a new ruling with its own false withholds.
