## Major

**M1. BOB-84's word edge rescans a token run once per span, which is quadratic** (`secrets.ts:154`).
- After merging, each span that ends inside a word is extended forward through the run of token characters
  after it. When many spans sit inside one token run, each extension walks to the end of that same run.
- The only pattern that leaves its span ending inside such a run is `slack_token`. Its class
  `[A-Za-z0-9-]` stops at `_`, which is a word character, and `-xoxb-` after the `_` starts the next span.
- Measured (best of 3):

  | Input | Time |
  |---|---|
  | `"xoxb-aaaaaaaaaa_-".repeat(16384/17)` | 108 ms |
  | `"xoxb-aaaaaaaaaa_-".repeat(200000/17)` | **16,292 ms** |
  | Luigi's `"xoxb-aaaaaaaaaa_"`, with no `-`, so no second span | 4 ms |

- Who it hits: `redactSecrets` runs only in the supervisor, in `withholdBody` and `withHandoff`. A
  worker's handoff, checkpoint or reply carrying this run blocks that laptop's supervisor loop for about
  16 s. The broker doesn't redact, so it isn't affected.
- Why a major: it is the same class as A-fixes-2's M3 (about 30 s on a 200 KB handoff), and it breaks
  BOB-84's own AC 4, "linear". It's my miss too: the sketch had no word edge, so I gave no linearity rule for
  one.
- **The fix, tested:** keep a cursor of how far the last extension scanned. Spans are merged and in order,
  so a span ending before that cursor ends inside the run already scanned:
  ```ts
  let scanned = 0;
  const edged = merge([...]).map(([s, e]): Span => {
    if (s > 0 && ...) while (...) s--;                 // unchanged
    if (e < scanned) e = scanned;
    else if (e < text.length && TOKEN.test(text[e - 1]!) && WORD.test(text[e]!)) { while (e < text.length && TOKEN.test(text[e]!)) e++; scanned = e; }
    return [s, e];
  });
  ```
  - With it, the 200 KB input takes 6.5 ms.
  - Over 300,000 fuzzed texts, the output is identical to bb51add's.
  - The backward edge is already linear. Every span holds a non-word character, or is word-bounded on both
    sides (`AKIA…`, `ghp_…`), so a backward scan stops at the previous span.
  - **Test:** add `"xoxb-aaaaaaaaaa_-".repeat(n / 17)` to the 200 KB inputs at `protocol.test.ts:353`.

## Minors
- **m1. A token match that starts inside an earlier match and runs past it leaves its tail.** This is
  older than this build: rc.41 does the same, and so does my sketch.
  - Each token pattern's spans come from `matchAll`, so its matches don't overlap.
  - `Bearer AAAA….Bearer BBBB…` gives `[mark] BBBB…`. The first match's class
    (`[A-Za-z0-9._~+/-]`) takes `.Bearer`, and `\s+` then starts the second token outside the first match.
  - `eyJa….eyJb….eyJc….eyJd….eeee` (a chain of 4) leaves `.eyJd….eeee`.
  - `findSecret(out)` is null in both cases, so the token goes out.
  - Neither shape is likely: two bearer headers glued by token characters, or a 4-part JWT chain.
  - §14 point 1's test property covers only `password_assignment`. Widen it to every pattern (my fuzz's
    check) and fix it as for assignments:
    - Bearer: its prefix `\bBearer\s+` at every keyword, its value the run of its class after the prefix.
    - jwt: a match goes through the run of `[A-Za-z0-9_.-]` it sits in.
  - Not for rc.42. Peach should capture it as a task.
- **m2. My sketch's "0 residual matches" was wrong.** It left a mark glued inside a word, so text beside the
  mark matched once marked:
  - `AKIAIOSFODNN7EXAMPLE` before a PuTTY header;
  - a Private-MAC's hex before `ghp_…`;
  - an END's `-----` before `eyJ…`.

  Luigi found these and fixed them with the word edge. My fuzz never glued fragments together, which is
  why it missed them. The fuzz saved with this review does.
- **m3. The stand-in audit is wider than BOB-87's AC 2.** Any reply sent as the stand-in, for any op, is now
  audited `remote:withheld`, not `remote:<op>` (`supervisor.ts:1114`). This is right, and it is the local
  audit table only. I'm noting it so that Peach's AC check isn't surprised.

## As ruled
- **BOB-84 (M1).**
  - Every span is found on the original text and unioned. Each merged span gets one mark.
  - The assignment prefix is found at every keyword. Its run comes from a pointer walk, and what it reaches
    from one right-to-left walk over the merged others (`secrets.ts:111`). This is the sketch's logic.
  - One difference from the sketch: `next` is replaced by a new span only if the new span starts left of
    it. This only keeps an enclosing span, and the fuzz agrees.
  - All of §14's must-redact cases are tested, as is the assignment-value property.
- **Departure 1, BOB-84's word edge.** A letter or digit before a span takes its word back, and a token run
  after a span goes with it (`secrets.ts:152-156`).
  - It withholds more, never less, and closes my m2.
  - The start condition (`ALNUM` before) keeps `DB_` in clear, since `_` is no boundary for the keyword.
  - The amount withheld is bounded by the glued word or run, and that word or run is part of a
    credential-looking string.
  - Accepted, with M1's cursor.
- **Departure 2, BOB-85's union with the stack.** As I answered Luigi's consult: each BEGIN goes through the
  first END of its kind after it, unioned with the stack's pairs (`secrets.ts:76-101`).
  - The first-END rule alone leaves `outer-tail` of `BEGIN A … BEGIN B … END B outer-tail END A` in clear. The
    stack pairs BEGIN A with END A and covers it.
  - Both walks are linear. The unclosed BEGINs come last, and those inside a line already found are skipped.
  - My fuzz's block rule (first END, or the BEGIN's own line) and the subset check against the sketch both
    hold.
  - §14 recorded the stack as withdrawn. It now records this union ("As built, A-fixes-3").
- **BOB-86 (M3).**
  - `jwt` is exactly the ruled regex (`secrets.ts:37`): `abc-eyJ…`, `x eyJ…` and `_eyJ…` are no longer
    detected, as accepted. 200 KB of `eyJ-`, `a-eyJ` or `eyJaaaaaaaaaaaa.` takes under 2.1 ms in `findSecret`
    and `redactSecrets`.
  - The `_detected` guard is on `secret` only (`secrets.ts:10`), case-insensitive through the pattern's `i`.
    `password_detected=…`, `PASSWD_DETECTED: …` and `api_key_detected=…` are detected.
    `secret_detected: …`, `SECRET_DETECTED=…`, the mark and the broker's refusal texts are not.
- **Linear, apart from M1.** Luigi's 18 inputs at 200 KB pass the 50 ms test. Mine, apart from M1's input,
  take under 7 ms each (best of 3). They include:
  - nested, crossed and END-first BEGIN/END runs, and PuTTY header runs, for the stack union (under 5 ms);
  - Bearer runs;
  - jwt chains;
  - `-AKIA…` and `_-sk-ant-…` runs;
  - `Private-MAC: ab_-ghp_…` runs.

## 5963584 (BOB-87): no wire or store change
- **Wire.**
  - A withheld `summary` now goes as the stand-in, `{v:2, event:"withheld", worker, re, req}`, with no
    `ok`. That is the shape `withholdBody` already sends for every other op (`supervisor.ts:1098`, `:1706`).
  - An rc.41 requester handles it the same as before. `copyFromReply` acts on `event: "withheld"` for
    `summary` whatever the `ok` (rc.41 `:1190`). With `ok: true` it went on and found no worker record and
    no `workers`, so nothing else happened then either.
  - Old and new talk both ways.
- **Store.**
  - `state_withheld` is BOB-78's existing column in the supervisor's `remote_workers`. It is now reset to 0
    in `copyView` and on a passing event (`:1188`, `:1261`).
  - The audit gets new action strings (`remote:withheld`) in the supervisor's local table.
  - Nothing reaches the broker's Durable Object store.
- **Behaviour, as ruled in point 6:**
  - one notice per withheld episode;
  - the summary stand-in goes without `ok`;
  - reconcile's withheld batches are reported in a `finally`, so a throw (an offline laptop) reports them
    too;
  - the timing tests warm up once and take the best of 3.
