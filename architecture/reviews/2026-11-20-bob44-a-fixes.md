# Review: BOB-44 build A-fixes, protocol and store (7d9e1d4..bf2203f, rc.41)

Toad, 2026-11-20. This is the architect's part of the review of build A's fixes: BOB-72 b2c8a96, BOB-73
c985339 and BOB-74 bf2203f, released as rc.41. I checked them against ADR 0007 §1-§9 and §14, my build-A review
(`reviews/2026-11-20-bob44-build-a.md`), the independent review (`lead/bob44/review-a-independent.md`)
and Mario's read (`lead/bob44/a-fixes.md`). My scope is where the fixes cross parts: `protocol/src/remote.ts`,
`protocol/src/secrets.ts`, the `remote_requests` rebuild in `store.ts`, the `state_dir` refusal, and the
withheld paths in `supervisor.ts`. The independent reviewer covers the two secrets fixes line by line.
Line numbers are at bf2203f.

**Verdict: signed off. 0 blockers, 0 majors, 2 minors.** Each fix answers its finding as the reviews
asked. Finding 1 only makes the known limit until B6 wider than `a-fixes.md` says.

## Findings

**1 (minor): until B6, the known limit also covers `status` and `list`, not only the `exit` and
`summary`.** `remoteView` (`supervisor.ts:1668-1683`) carries the worker's `error` and `checkpoint`.
So a multi-line `error` that matches only once serialised (the old pattern, which is still the
broker's) gets every body that names that worker refused: its `exit`, the `status` that the requester
asks after the stand-in (`:1170-1172`), and every `list` batch that includes it. I checked with node:
`error: "… api_key:\n\nexport it first"` doesn't match as a field under either pattern. In the
serialised body it matches the old pattern and not the narrowed one. Until B6:

- The copy never ends, and poe isn't told. `a-fixes.md` says "the exit's state arrives by `status`",
  but that holds only when the match is in the handoff, not in `error`.
- `reconcileNow` returns at a withheld `list` (`:1357-1358`), so the later batches for that laptop
  aren't asked either. Every copy behind the bad one stalls until B6.

It heals itself once B6 is deployed: the next reconcile's `list` passes, and the copy ends with
`summary`, or with `summaryWithheld` if the handoff is the problem. **Fix:** (a) correct the known
limit in `a-fixes.md` and the rc.41 notes ("`status` and `list` too, when the text is in `error`").
B6 (BOB-71) should be deployed soon after rc.41 is on both laptops, and before §12's retirement of
poe@ubu1. (b) In `reconcileNow`, a withheld `list` reply should go on to the next batch and report
the withheld one at the end, so one worker can't hold up the rest. It isn't a laptop that can't be
reached. (b) is Luigi's, and can wait for build B. Don't add the old pattern back on the target (see
Mario's note). After B6 it would withhold more than the broker refuses.

**2 (minor): the rebuild's `ROLLBACK` can hide the error it is cleaning up after**
(`store.ts:217-220`). Some errors (SQLITE_FULL, IOERR, NOMEM) make SQLite roll back by itself. The
`ROLLBACK` then throws "no transaction is active", and that message replaces the real cause. The
supervisor doesn't start in either case, and nothing is lost. Only the log is wrong. **Fix:** guard the
`ROLLBACK` (`if (this.db.isTransaction)`, or a try around it) and rethrow `err`.

## Rulings on what crosses parts

**The schemas on read (`remote.ts:65-94`, `supervisor.ts:1116-1129`): as finding 2 of my build-A
review asked.**
- `RemoteWithheld` matches §14's stand-in field for field. `RemoteExit` limits `state` to the three
  ended states, which are exactly `ENDED_STATES` (`:153`) and the `WorkerState` ends (`store.ts:12`).
  `View` requires a string `id` on `worker` and `workers[]`, which closes the independent review's
  minor 5. `remoteView` always gives `id`, and no reply sends `worker: null`.
- The objects stay loose, so a newer target's extra fields pass. A newer target's new event name or
  exit state is logged and dropped. That is right for an old requester, which can't act on it.
  Reconcile still sees the end.
- The order keeps §2's additive rule. A `v`-less non-answer is dropped before the schema, as before.
  A reply stand-in is told apart by `event: "withheld"` with a `req`, so it reaches `req` matching even
  without `v`. A `v`-less reply from an rc.38 target fails `RemoteReply` and is dropped, as it was
  before (only the log level changes, from info to warn).

**The `v: 2` stand-in.** `withheldBody` (`:206-219`, unchanged in this range) copies `v` only when the
refused body had it. rc.39 and rc.40 do the same, so in a mixed field every `v: 2` event stand-in
passes the gate, and a `v`-less one is dropped, as §9 is now ruled.

**`withholdBody` and `withHandoff` against §2: the fix my build-A review asked for.** Each field is
redacted, the serialised body is checked, and then the matching field is withheld whole, the handoff
as `handoff_text: null, handoff_withheld: true` (`:196-203`, `:300`). With the narrowed
`password_assignment`, no pattern can match across a JSON escape or a field boundary. So with today's
patterns the body check never fires, and it stays as the guard against drift. (The `detect`
injection exercises it in tests.) The cross-field case that `withholdWhole` can't split can't occur,
as Mario notes, and the broker's stand-in covers it anyway. Two small notes, with no fix needed:

- The comment at `:315` ("a cut can end a span … a `\b` at its end") describes nothing that can happen.
  No pattern has a trailing assertion, so a prefix matches only where the whole text does. The
  re-check is harmless.
- If it ever fired, a redaction mark longer than its span could push the cut body past the fit. That
  can't happen while it can't fire.

**The requester's withheld end: my finding 1's fix as I asked for it, and §2's "the orchestrator asks
the role on the target".**
- An `exit` that carries `handoff_withheld` ends the copy with "handoff withheld: ask <name> on
  <laptop>" (`:166`, `:1272`).
- A withheld `summary` for an ended copy without a handoff ends it the same way, and it isn't asked
  again (`:1190`, `:1250-1254`). Once its handoff is non-null, reconcile skips it (`:1320`, `:1348`).
- A withheld event for a copy that hasn't ended asks `status` (`:1170`). A withheld `exit` loses its
  `lands` (the notice has no "Land:" line). That is what a stand-in costs, and it is acceptable.

**The secrets changes: what the broker has to carry.**
- The narrowed `password_assignment` changes `findSecret`, so the broker refuses less only after B6
  (BOB-71). The `private_key` span changes only `redactSecrets`, so it needs no deploy.
- **B6 can be deployed in any order against the laptops.** An rc.40 target redacts each field with the
  old, wider pattern, and the narrowed broker refuses nothing that this lets through. An rc.41 target
  is consistent with the narrowed broker.
- **A correction to my build-A review.** It said "an old broker still refuses more, which the target's
  body check above catches first". As built, it doesn't: the target checks with the narrowed
  detector. Until B6 the broker refuses, and stand-ins carry the end, with the reach in finding 1.
  This is also noted in ADR 0007 §14.

**For Peach and Casper, not ruled here (what counts as a secret):**
- After B6, a `password=`/`secret=`/`api_key=` value with a `\` before its eighth character is no
  longer caught, for example a Windows path or an escaped string.
- A BEGIN line with no END line now withholds the rest of the field. Before build A, the whole body
  was refused.
- `-----BEGIN PGP PRIVATE KEY BLOCK-----` doesn't match `private_key` at all. This is older than these
  fixes.

**Store: the `remote_requests` rebuild (`store.ts:206-221`): signed off (my build-A finding 3).**
- `BEGIN IMMEDIATE` takes the write lock before the RENAME. A crash or a busy db leaves the old table
  and its dedupe rows, and the next start rebuilds.
- The `notnull` check is read outside the transaction. That is safe because the pid file check in
  `bin.ts:52-60` exits a second supervisor before `new Store` (`:69`).
- mbp-1 and ubu1 have already rebuilt, so this is a no-op for them.

**The `state_dir` refusal (`config.ts:480-486`, `bin.ts:45-49`): signed off (my build-A finding 4).**
- It refuses only when `state_dir` is absent and the old `<cwd>/~/…/supervisor.db` exists. It moves
  nothing, and it names both paths and both ways out.
- It runs before the pid file and the db, and the main path is the only one that opens the db.
- Under launchd or systemd, exiting with 1 means the supervisor restarts in a throttled loop that logs
  the same line. That is the refusal working, not a bug.
- It reads the same cwd that rc.38 wrote under, as long as the unit's working directory hasn't
  changed.
