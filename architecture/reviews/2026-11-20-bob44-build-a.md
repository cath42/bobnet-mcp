## Protocol: classification and the loop guard

`classifyRemote` (`protocol/src/remote.ts:89-104`) treats a body as a request only when it is one JSON
object with `op`, no `in_reply_to`, no `re` and no `event`. `onRemote` (`supervisor.ts:1005-1035`)
answers only a request, and `onRemoteAnswer` (`:1042-1062`) never sends anything. I checked every body
that can reach a supervisor in a mixed field:

- **A new target's `v: 2` replies** have `re` and `in_reply_to`. When they are resent without
  `in_reply_to` they still have `re`. Its events and withheld stand-ins have `event`. Restart replies
  (`:455-461`) have `re`. None of them is a request.
- **A `v`-less reply** (`{ ok, op }`, for hand-written requests and the `v`-less restart reply) is sent
  with `in_reply_to`. Read on its own it would be a request, so `flushRemote` never resends it
  without `in_reply_to` (`:2493`). If the broker refuses it with `unknown_message`, it is dropped and
  audited. The guard checks the body itself, not its `v`, so it also covers a body that a later
  release adds.
- **A new requester and an rc.38 target.** The version check refuses first (`:1371`). If the version
  doesn't parse, rc.38 refuses `v` and answers with `in_reply_to`. The requester reads that as a
  reply with no `req`, drops it, and the exchange ends after one step.
- **A requester rolled back to rc.38.** rc.38 reads any object as a request, so it answers a `v: 2`
  event or reply as malformed, with `in_reply_to`. The new target reads that answer as a reply that
  matches nothing and drops it. The exchange ends after one step.
- **A hand-written `op` body sent with `in_reply_to`** is now taken as a reply and isn't answered.
  rc.38 answered it. §2 decided this ("has no `in_reply_to`"), so it isn't a finding. A hand-written
  request must be a new message.

**`v` handling.** `parseRemoteRequest` (`:120-130`) routes only the number 2 to `RemoteRequestV2`.
Anything else, including `"2"`, goes to today's strict schema and fails with "v is not allowed". That
is §2's additive rule: an old target refuses and runs nothing. The `v: 2` schemas are `.strict()`, they
refuse a path (`handoff`, `resume_session`) and `as: "lead"`, and they cap `ids` and `reqs` at 100 and
`tail.n` at 500.

**Version compare** (`:147-160`). Rc numbers compare numerically, a release sorts after all of its
rcs, and a missing or unparsed version returns null, which means "send" (§9). Only a parsed version
that is older refuses. The peer it reads is the pinned `supervisor` name on that laptop (the broker's
`forbidden` "is the supervisor on", `broker.ts:218`), so another process can't fake that version.

## Store: migrations on a live supervisor db

- **Additive.** The change adds two nullable columns on `workers`, two on `outbox` (`in_reply_to`,
  `ttl_seconds`), and two new tables (`remote_sent`, `remote_workers`). Each is guarded by
  `PRAGMA table_info`, so the migration is a no-op on mbp-1 and ubu1, which already ran rc.39 and rc.40.
- **The `remote_requests` rebuild** (`store.ts:205-213`) runs only while `reply` is still NOT NULL,
  which means once. It copies every row, and the new `v` defaults to 1. Finding 3 covers the rebuild
  not being atomic.
- **A rollback to rc.38 is safe on a migrated db.** rc.38's `recordRemote` inserts without `v`, which
  defaults to 1. Its `remoteReply` reads an in-progress row (reply null) as unseen and handles it
  again. Its flush reads only kinds `message` and `board_op` (517ec3a^ `supervisor.ts:1666,1683`), so
  `remote` rows wait, unsent, for the next rc.39+. Its `createWorker` leaves `remote_by` and
  `spawn_req` null.
- **`remote_sent` and `remote_workers`** match §7, with ADR 0007's three tables cut to two for A
  (`remote_asks` is B). `message_id UNIQUE` allows the many nulls of rows the broker never took.
  `laptop COLLATE NOCASE` in the key makes `remoteCopy` case-blind, as addresses are. None of the
  tables is ever pruned, the same as `workers`, `audit` and `remote_requests`. `remote_sent` grows
  with use, plus one `list` every 5 minutes while a copy isn't ended. Any pruning later must keep
  each spawn row that a copy names: the strict event check looks it up (`:1078-1080`).

## Outbox, matching, copies

- **Final codes** (`:130`) are the broker's permanent refusals for a send (`broker.ts:123-145, 301-303,
  637`) plus the supervisor's own `too_long`. Every other code (`not_hosted` before registering, no
  connection) waits, and the rows behind it wait too. The broker queues for an offline peer it knows,
  so one requester that is away doesn't block the others.
- **The withheld stand-in** (`:174-189`) keeps `re`/`req` on a reply. `onRemoteAnswer` takes it as
  the answer (`:1045`), and the tool says the reply was withheld (`:1461`).
- **`req` matching** accepts a reply only from the address the request went to (`:1052-1056`). Copies
  are written before the row settles, so "spawned after all" still sees `unanswered` (`:1057-1060`).
  The broker's ack resolves before the target's reply can be read, so `remoteSentAs` (`:1328`) has
  always run first.
- **The strict event check** (`:1076-1083`) is right, for §14's reason. `onRemoteAnswer` is
  synchronous from read to write, as §7 asks.
- **Copies only forward** (`copyView`, `:1133-1158`): an ended copy with a view is final, a copy
  made from an `exit` takes its first view and keeps its state, a url is never cleared by a null, and
  `told` is persisted.
- **Reconcile** (`:1219-1265`) runs per laptop and one at a time. It asks in batches of 10, stops at
  the first failure, never marks `unknown` from a truncated list, and its `reqs` reach back one day
  (the replies' ttl).

## Findings

**1 (minor): a withheld `summary` reply leaves an ended copy without its end notice.** A copy that
ended without its handoff asks `summary` (`copyEnd`, `:1168-1171`). Suppose the broker refuses that
reply as a credential: our redaction missed the span, but the broker's detector, newer than the
target's protocol package, caught it. The stand-in then reaches `copyFromReply`, which returns at
`ok !== true` (`:1108`). The copy's `handoff` stays null and poe is never told the worker ended.
Every reconcile asks `summary` again (`:1222`, `:1254`) and gets the same stand-in. ADR 0007 §2 says
that what is withheld is the role's to tell ("the orchestrator asks the role on the target"); the
requester has to say it. **Fix:** in `onRemoteAnswer`, when `sent.op === "summary"` and the answer is
a withheld stand-in, store the copy's handoff as `{ handoff_text: null, handoff_withheld: true }` and
call `copyEnd`. Its notice then says "handoff withheld (the broker took it for a credential): ask
<role> on <laptop>". An `exit` that arrives as a stand-in needs nothing: reconcile ends the copy and
this path covers its handoff. Test: a FakeNetwork whose broker detector refuses a pattern that the
target's doesn't.

**2 (minor): the protocol's reply and event schemas aren't applied.** `RemoteReply` and `RemoteEvent`
(`remote.ts:66-77`) are used only by tests. The supervisor reads raw JSON. For example
`String(json["state"])` (`:1094`) treats any value, even a missing one ("undefined"), as an `exit`'s
ended state. `RemoteEvent` also requires `worker` and `spawn_req`, which the withheld stand-in that
§14 describes may not have. The wire is defined once (§2) but nothing checks it on the read side, so
two releases can drift apart without a test noticing. **Fix:** in `protocol`, add a `RemoteWithheld`
schema (`v?`, `event: "withheld"`, `worker?`, `spawn_req?`, `re?`, `req?`) and an `exit` schema whose
`state` is `done | failed | stopped`. In `onRemoteAnswer`, `safeParse` replies with `RemoteReply` or
`RemoteWithheld` and events with `RemoteEvent`, then log and drop anything that fails. Keep the
schemas loose, as now, so a newer target's extra fields still pass (the additive rule).

**3 (minor): the `remote_requests` rebuild isn't one transaction.** `store.ts:207-212` runs RENAME,
CREATE, INSERT and DROP as one `exec`, without `BEGIN`. If the process dies after the RENAME, the next
start's `SCHEMA` creates an empty `remote_requests`. The check then sees `reply` nullable and skips
the rebuild, so the dedupe rows stay in `remote_requests_old`, and a redelivered old request would
run a second time. If another connection holds the db past `busy_timeout` (2 s), the RENAME throws and
the supervisor doesn't start. **Fix:** wrap the rebuild in `BEGIN IMMEDIATE` … `COMMIT`, with
`ROLLBACK` on a throw, as the broker's migrations do (`board.ts`, `transactionSync`). This changes
nothing for mbp-1 and ubu1, which have already rebuilt; it matters only for dbs still on rc.38.

**4 (minor): rc.40 moves the db and pid file of any laptop without `state_dir`.** `state_dir` places
`supervisor.db` and `supervisor.pid` (`bin.ts:47, 64`), as well as the handoffs. Before 28f4cc0
(`config.ts:196`), a laptop without `state_dir` ran from `<cwd>/~/.local/state/bobnet`. On rc.40 it
opens `~/.local/state/bobnet` instead: a new or stale db, without its workers, outbox, remote_sent,
copies and dedupe rows. On ubu1, poe@ubu1 moved the files by hand before the restart, and mbp-1 sets
`state_dir` (`lead/bob44/ac10-evidence.md`). Any other laptop, or a fresh install from an older
config, would quietly start over. **Fix:** a line in the next release notes. Also a start check: when
`state_dir` isn't set and `<cwd>/~/.local/state/bobnet/supervisor.db` exists, refuse to start and name
both paths and the move. Don't move the files automatically: the supervisor would be moving files on
the laptop that belong to Casper.

**5 (minor): `redactSecrets` adds `g` to every pattern's flags** (`secrets.ts:25`). If a pattern ever
has `g` itself, `new RegExp(source, "gg")` throws, and so does every reply and event that
`withholdSecrets` runs on. `findSecret`'s `test` would also become stateful. None of the patterns has
`g` today. **Fix:** `re.flags.includes("g") ? re.flags : re.flags + "g"`, and a comment on `PATTERNS`
that a pattern has no `g`.

## Ruling: the §9 `v`-less `exit` and `remote_control` (§14 open item)

**No fix, in review A or in build B. §9's sentence "The requester accepts a `v`-less `exit` or
`remote_control` from a target for a worker it has a copy of" is struck.** The case it was written for
can't occur:

- A target is rolled back only through a restart. rc.39's shutdown stops its `v: 2` workers, and their
  `exit` (`v: 2`, with `spawn_req`) goes into the `remote` outbox. If the process dies first, rc.38
  fails them at start, and that start sends no event (517ec3a^ `supervisor.ts:269-283`; its
  `remoteEvent` is called only at a live end and a url, `:970, :1506`).
- No `v: 2` worker runs under rc.38: none survives the restart, and rc.38 can't spawn one. If rc.38
  answers an orphaned request and resumes the worker, the resumed worker gets a new id (`:584` copies
  `spawned_by`). Its `v`-less events name a worker that has no copy and no `spawn_req` to check, so
  accepting `v`-less events would still not make that copy. In A and B before poe@ubu1 is retired,
  poe@ubu1 is the one who answers there.

What remains is a copy left not ended while its target is below rc.39. That is already covered. The
copy shows its last state with `as_of`. `worker_status` and `worker_summary` answer from the copy,
with `from_copy` naming the version refusal (`remoteCall`, `:1431-1440`). Once the target is back on
rc.39+, its queued `exit` goes out (rc.38 never flushes kind `remote`), or else reconcile lists the
id as failed and `summary` brings the handoff. Accepting `v`-less events would also weaken the strict
check (§14): an event without `spawn_req` can only be tied to its sender's laptop. I've added a line
to ADR 0007 §14 pointing here.
