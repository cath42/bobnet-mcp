## Findings

### M1 (major): a request copy that missed its `settled` stays open on the requester for good

The requester changes a request copy only from `askCopy` (`supervisor.ts:1348-1371`). Two things call it: an event,
and a `list` reply's per-worker `requests` (`:1410-1414`). A list names only open and orphaned requests (`:1947`).
So a settle the requester never received is never learnt, and no copy is ever pruned. `pending_requests` then lists
the copy indefinitely (`remotePending`, `:943-955`). Answering it gets "r_… is already expired".

This happens in ordinary ways:
- **The requester is away more than a day.** The `settled` event expires at the broker (ttl 86400, §2). If mbp-1 is
  closed over a weekend while a request waits, the target's timeout denies it, and the `settled` is gone by the time
  mbp-1 is back. §2 says "a requester away for longer recovers by reconciling (§7), which doesn't need them". That
  holds for worker copies, not for request copies.
- **The `settled` is withheld or undeliverable.** The stand-in carries no request id.
- **A target rolled back below rc.43.** Its next start orphans without the hook, so no `settled` is sent, and its
  `list` has no `requests` key.

**Fix** (requester only, no wire change):
1. When a `list` reply is not `truncated` and a worker's view carries a `requests` **array**, any open or orphaned
   copy of that worker's that is not in the array is final. Use a new state such as `gone`, rank 2: the requester
   doesn't know whether it was answered or expired, so it shouldn't guess. A view without the key (an older target)
   changes nothing.
2. `pending_requests` leaves out an open or orphaned copy older than a day. That is the bound a local orphan has
   (`expireOrphans`), and an open request on the target is denied by its timeout well before then. This covers a
   rolled-back target and a worker that isn't listed any more.
3. Prune final copies after a day, as unacked rows are.

Test: a copy left open with no `settled`, then a list showing the worker with `requests: []`, then the copy is final
and `pending_requests` is empty. Also: a view with no `requests` key leaves the copy as it was.

Reconcile already lists every copy that isn't ended, so (1) costs nothing more. A worker ended with an open copy is
covered by (2).

### Minors

- **m1. The `answer` op doesn't check that the worker is `v: 2`** (`ownRequest`, `supervisor.ts:1989-1996`). A
  `v`-less remote spawn's requests go to the target's orchestrator (§4, §9). Its sender, if it sends a `v: 2`
  `answer` by hand, can answer them too: two answerers. The auth is the same as §4's (the sender's own worker), so
  this isn't a widening. Fix: for `answer`, refuse a non-`isV2` worker's request with "its requests are answered on
  <laptop>". `request`, which only reads, may stay.
- **m2. `by` is unbounded, but the snapshot caps it.** The `v: 2` spawn's `by` is `z.string().min(1)`
  (`protocol/src/remote.ts:46`). It becomes `remote_by`, which the snapshot sends under the broker's `max(40)`
  (`frames.ts:125`). It also goes verbatim into the worker's preamble (`supervisor.ts:2235`). A `by` over 40
  characters would make the new broker refuse the target's whole report for that worker's life. That isn't reachable
  today: the requester sends `orchestratorOf`, a segment of at most 32. Fix: the target refuses a `v: 2` spawn whose
  `by` fails `isValidSegment` (`protocol/src/address.ts:6`). That needs no schema change. Not a deploy blocker.
- **m3. "Spawned after all" fires for every later copy of the same spawn.** `copyMade` (`supervisor.ts:1514-1520`)
  checks only the spawn row's state. An adopted row stays `unacked`, and an unanswered one stays `unanswered`. So a
  resume or a reset of that worker on the target (a new id, the same `spawn_req`, BOB-66 AC 7) tells poe "X spawned
  after all" again, for a worker poe resumed itself. Fix: notify only when no other copy has that `spawn_req`.
- **m4. `fitRequest` doesn't cut `answers` and doesn't check that the result fits** (`supervisor.ts:270-277`). A
  settled question with large answers, read by the `request` op, can exceed the body. Its reply is then `too_long`
  and dropped, and `request_detail` says "may or may not have run". Fix: cut `answers` too. If the result still
  doesn't fit, send `input` as a stub with `truncated`.
- **m5. A withheld `request` or `answer` reply gives the wrong advice** (`supervisor.ts:1859`): "list_workers … shows
  what ran". For `answer`, it should say the answer may have been taken and the copy clears with `settled`. For
  `request`, it should say to ask the role on that laptop or use the dashboard.
- **m6. Mixed versions: §9's "either order is safe" no longer holds** (point 4 below). The rc.43 notes' order rule
  covers it. A code guard would make it hold again: the target refuses a `v: 2` spawn from a requester whose
  supervisor is below rc.43, read from the peer list as the requester reads the target's (§9). Backlog, not this
  fix loop.
- **m7. Tests still missing a real requester and a real target together** (point 3 below):
  - `answer_request` with `resume` on an orphaned remote request, through the requester's tool, checking the reply's
    `resumed` and the `resumed` event's new copy;
  - a question answered through the requester's tool (`answers`).
  
  Both read correctly today (`RemoteReply` is loose, and `answers` matches `remote.ts:60`), so this is a minor, not
  a bug.

## Rulings on the points Mario flagged

### (1) BOB-66's departures: all accepted

- **A shutdown leaves waiting requests open, and a stop settles them** (`router.ts:201`). Accepted. §4's "the abort
  path settles its row … for every worker" was written for a stop. A graceful restart (an upgrade's `now`, poe's
  restart) must leave the row for §4's "A target restart" to orphan, or answering could no longer resume the worker.
  The test "a shutdown's request stays open…" carries it. A crash also leaves it open, and the next start orphans it.
  Recorded in §14.
- **Field names.**
  - `request` (the request id) in all three events, not `id`. §2's events use `worker` for the subject, so `id` would
    be ambiguous.
  - `settled` is `{request, state, decision, decided_by}`.
  - `resumed` is `{worker: <new>, previous, request}`. Putting the new id in `worker` lets the generic event path make
    the new copy with no special case. That is the right choice: the subject of an event is the worker that exists
    now.
  
  Accepted, and recorded in §14 as the wire.
- **The `v: 2` test: `remote_by && spawn_req && spawned_by` with `@`** (`isV2`, `supervisor.ts:3415`). Accepted. The
  three are set together by a `v: 2` spawn and carried together by `remoteOf`, so the extra terms only guard a
  half-written row. What §4 asked for holds: one test, in one function. BOB-68 made `v2Event`, `pending`,
  `remoteAnswerer`, the notices and the preamble all call it. The snapshot (`:3292`) and the dashboard key on
  `spawned_by` with `@` and `remote_by`. That is the same set for every row a spawn can write.
- **`reset` carries `remote_by`/`spawn_req` only when `spawned_by` is kept.** Accepted: a reset by another caller
  makes the worker that caller's.

### (2) BOB-67: all accepted

- **The worker is checked before the entry** (`ownRequest`, `supervisor.ts:1989-1996`). Accepted. The entry check
  needs the request's worker, so running it first would tell any `remote` sender whether another sender's request
  exists. An unknown request and another sender's are refused with the same text. §4's order is amended in §14:
  sender in `remote`; the request is the sender's worker's; the entry; open or orphaned. The entry check still comes
  before any effect, which is what §4's order was for.
- **"The config at the time of the answer" is the config read at the last start.** Accepted. There is no reload, so
  the two are the same, and §4's words hold. In practice, removing an entry needs a restart, and the restart fails the
  worker. So the entry's removal ends answering for its orphans: the test reboots ubu1 with the role taken out. To cut
  off a live worker, Casper stops it on the dashboard. The `config.ts:213-225` comment says so. Recorded in §14.
- **The remote orchestrator's `user_decided` decides human-tier requests as a local one's does.** As designed: §4
  "What that grants", said plainly for Casper. The target's audit shows it. The `answer:<decision>` row has
  `decided_by: human`, and beside it the `remote:answer` row has actor `supervisor@mbp-1` and `by: human`. So a remote
  human-tier decision can be told apart from Casper's dashboard answer by the second row. No change.
- **The `request` reply carries the full RequestRow through `withholdBody`.** Sound. `withholdSecrets` and
  `withholdWhole` recurse into nested objects (`supervisor.ts:191-205`), so `request.input`, `reason`, `message` and
  `answers` are each redacted, and the serialised body is checked as the broker checks it. The row is the spawner's
  own worker's request, so sending its other fields (`decided_by`, `answers`) shows nothing it may not see. The
  remaining limit is the fit (m4).
- Also accepted:
  - the audit's `by` (`human` when `user_decided`, else `orchestrator`);
  - `list`'s per-worker `requests` (`supervisor.ts:1947`);
  - `request_detail` on the target still reading a `v: 2` worker's request. §4 asks only `pending_requests` and
    `answer_request` to leave it out, and reading answers nothing.

### (3) The test gap BOB-69 found

The rename was needed. The requester's `RemoteReply` types `worker` as a view (`protocol/src/remote.ts:85`), so B2's
string `worker` failed the parse, and every remote `answer_request` would have timed out. B2's tests had a scripted
sender, so nothing read the reply with the requester's schema.

**Where it stands after BOB-69.** These now have a test where both ends are the real supervisors (`real()` and
`remoteAsking()` in `requests.test.ts`):
- the `request` and `answer` ops and replies (`request_detail`, `answer_request` allow and refusals, AC 5's one
  tool);
- the `request` and `settled` events (BOB-68 AC 4, BOB-69 AC 3);
- `list`'s `requests` (BOB-75 AC 3).

These are still played or scripted on one side:
- `answer` with `resume` through the requester's tool, and the `resumed` event as the requester handles it (AC 7
  resumes on the target directly);
- a question's `answers` through the requester's tool;
- the withheld stand-ins of the new replies (m5);
- an older target's `list` without `requests`.

I read each one against the schemas, and none is broken. The first two are m7. **The rule for build C and later:**
every field a build adds to a reply or event gets one test where the real requester reads what the real target
sends. Played targets are for orders and timings.

### (4) §9: mixed versions for the new events and ops

- **rc.43 requester, rc.41/42 target:**
  - The target refuses `request` and `answer` cleanly ("doesn't serve v: 2 … yet", since build A).
  - Its `v: 2` workers' requests still go to its own orchestrator, as rc.42 does, and poe@ubu1 answers them.
  - Its `list` has no `requests`, and `copyFromReply` reads only an array.
  - The bare `list` (BOB-75) is build A's "its live ones".
  
  Safe.
- **rc.42 requester, rc.43 target:** not safe, and the rc.43 notes are right to put the requester first.
  - rc.42's `REMOTE_EVENTS` already has `request`, `settled` and `resumed`. So the events parse, keep the worker copy,
    and tell nobody (§14, build A).
  - The rc.43 target no longer tells its own orchestrator (B3), and its `pending_requests` leaves them out.
  - So a `v: 2` worker's request reaches only the dashboard (Casper) or the timeout's deny. The worker's Remote
    Control failure and the restart notice also reach nobody.
  
  §9's "Either order is safe" is struck for rc.43 in §14. The notes' rule stands: mbp-1 on rc.43 first, and no
  cross-laptop spawn while ubu1 runs rc.43 and mbp-1 doesn't. **Note for Mario:** the notes offer Casper "one hand
  install" of rc.43 on ubu1. That option must come after mbp-1 runs rc.43, or come with that no-spawn rule said to
  poe. The guard that makes it hold in code is m6.
- **A target rolled back from rc.43 to rc.42:** its open requests are orphaned with no `settled`, so the requester's
  copies stay open. That is M1, whose fix (2) covers it.
- **The new snapshot fields:**
  - An rc.43 supervisor talking to today's broker: `WorkerSnapshot` is a stripping `z.object`, so the fields are
    dropped (protocol test).
  - An rc.41/42 supervisor talking to the new broker: the fields default to null, and the dashboard shows no spawner.
  - `StatusStuckRun.laptop` is optional, so an old broker sends none and the dashboard shows none.
  
  Safe in any order, as §9 says.

  text ever changes, it fails toward `unacked`: extra bare lists for a day, and "may or may not have run". Both are
  safe. A distinct client code (`not_connected`) is an additive client change for the backlog, not this loop.
- **BOB-75 departures.** All accepted:
  - `unacked` applies to every op, but only spawns are adopted;
  - an adopted row keeps `unacked` (with m3's fix);
  - every `sent` row becomes `unanswered` at start, since no wait survives a restart. This widens AC 5 safely;
  - a spawn's loss starts a reconcile at once.
  
  Another departure narrows §7's "unknown workers are learnt": a bare list's other unknown workers make no copy. That
  is accepted and consistent with build A's ruling that an event is taken only for a spawn sent there.

  - the result shape `{id, state, decision, resumed?, laptop}`;
  - `request_detail` with no fallback to the copy (§5 gives a fallback only to `status` and `summary`);
  - the orphaned notice, told once on the move to orphaned.

  - `remote_by` is sent only beside an address `remote_from`;
  - "waiting on poe@mbp-1" only for a `v: 2` worker. A `v`-less remote spawn's requests go to the target's
