## 1. Findings

### m1 (minor): only a worker's exit is kept from poking the upgrade during a shutdown
- **What BOB-93 changed.** A worker's exit no longer pokes the upgrade while the supervisor shuts down
  (`supervisor.ts:2851-2853`). Two other paths still poke during a shutdown:
  - a slot's release (`onSlotReleased`, `:3294`);
  - a remote request finishing (`:1275`).
- **How it is reached.** Take a `now` upgrade that is waiting on a slot run, such as a land mid-push.
  1. A SIGTERM arrives.
  2. `shutdown()` waits for the runs (`:680-690`).
  3. The land ends, and its `finally` releases the slot.
  4. `poke()` (`upgrade.ts:411`) now finds the laptop idle for `now`.
  5. `switchAndExit` switches `current` under the shutdown.
- **What follows.** This is the behaviour before BOB-93, so it is no worse than rc.44:
  - the next start comes up on the new release and says `ready`;
  - or, if the store is already closed, `moveUpgrade` throws inside a `void` promise as the process exits.
- **Fix.** Guard the poke in one place, not at each caller. Either:
  - `UpgradeHost` gets `closing(): boolean` and `poke()` returns when it is true; or
  - the supervisor's four poke sites (`:659`, `:1275`, `:2852`, `:3294`) go through one `pokeUpgrade()` that checks
    `this.closing`.

  Test: a `now` upgrade waits on a slot, `shutdown()` starts, and the slot is released. The row stays `waiting` and
  `switch` isn't called.
- **When.** Backlog.

### m2 (minor): exec's timeout kills only the child, then returns at once
- **What BOB-95 changed.** `exec` now resolves at its timeout (`upgrade.ts:81-87`). That is right: before, a
  grandchild holding the pipe (git's ssh) kept the call open past every deadline.
- **What is left.** `SIGKILL` reaches only the direct child. Its own children live on after `exec` has returned:
  - **After a fetch:** ssh may keep running and still hold the ref lock. An "ask again" soon after then fails
    `cannot lock ref`. The error says why, and the next try works.
  - **After a `pnpm install`:** pnpm's lifecycle scripts may still write into `.<tag>.partial` while `clean()`
    removes it. That can leave files behind, or `rmSync` throws `ENOTEMPTY`. `run()`'s catch still reports
    `failed` ("install"), and the next build of the tag clears the folder first.
- **Fix.** Start the child in its own process group (`detached: true`) and kill the group on timeout:
  `process.kill(-child.pid, "SIGKILL")`, falling back to `child.kill`.
- **When.** Backlog, with the next `upgrade.ts` change.

## 3. The departures

### BOB-94: the guard

**Case folding always, ubu1's case-sensitive disk too. Accepted.**
- On APFS, folding is required: `~/.local/share/BOBNET` is the same folder as the guarded one.
- On ext4, folding only adds denials, for a folder whose name differs from a guarded one only in case. No worker
  has a reason to write such a folder, and a deny is the safe error.
- One rule for both laptops is simpler than reading each disk's case behaviour.

**A same-prefix sibling now passes. Accepted, and this is the intent.**
- The guard protects folders. `~/.config/bobnet-old` and `~/.local/share/bobnet.bak` aren't those folders.
- The old substring test denied them. That was a false deny, never a protection.
- What really is inside a guarded folder is still denied:
  - the folder named whole, then `/` (`named`, `(?![\w.-])`);
  - `.<tag>.partial` and `.src.git`, which sit under `<root>`.
- The token file is still denied by name, wherever it is (`/\bsupervisor\.token\b/`).

**Relative words resolved from the cwd, without a cd. Accepted.**
- A Bash command runs in the worker's cwd, so that is where a relative word points.
- For a false deny, the cwd must be the parent of a guarded folder and a non-path word must match a guarded name.
  For example, `cd ~/.local/share && grep bobnet x` denies. That is narrow, and it errs toward the deny.
- Not covered, as the log says: globs, other variables (`$XDG_DATA_HOME`), `eval`, `$(…)`, and words past the
  256th. The guard is a best effort. The sandbox's `allowWrite` is the enforcement (ruling 4).

### BOB-93: the row's stages

**The extra `waiting` stage. Accepted, and needed.**
- Without it, a restart while waiting for idle leaves an `installing` row.
- `resume()` would then report "restarted while installing" for a release that is fully installed, and discard a
  partial that no longer exists.
- With `waiting`, the new process says the right thing: "stays installed, so asking again switches to it".
- `stage` is TEXT, so this needs no migration. The schema stays additive (§6).

**No poke on a worker's exit during a shutdown. Accepted.**
- A shutdown's stops aren't idle. A SIGTERM is someone stopping the supervisor, perhaps to roll back by hand (§6).
  Switching `current` under it would be wrong.
- The next process fails the waiting row (step `wait`). The release stays installed, so asking again switches
  straight to it.
- The guard isn't complete: m1.

**A rollback to rc.44 leaves `installing` and `waiting` rows unread. Accepted, harmless.**
- rc.44's `resume()` reads only `restarting`. An open row from rc.45 is left alone, and nothing breaks.
- Such a row exists only if rc.45 was restarted mid-install or while waiting, and the next process is rc.44 (a
  rollback by hand at that moment).
- The next rc.45 or later start then sends a late `failed`. That is true, and the requester takes it only for a
  `req` it sent.

### BOB-95: the drain and exec

**A new refusal reason for a remote spawn during the drain. Accepted** (my consult c_81760beb, now recorded).
- It uses the existing reply, `{v: 2, re: "spawn", req, ok: false, error}`. Only the `error` text is new.
- The requester doesn't read the text: it gives it to the orchestrator as written. No requester's behaviour
  changes, so this isn't a protocol change.
- It isn't a limit. A v2 remote spawn is never queued (ADR 0007 §3), so refusing is the only honest answer.
- The text says when to ask again.

**Should ADR 0008 §4 record the drain hold? Yes.**
- Recorded in "As built, build C". It says more than §4 step 4: from the switch to the exit, no queued worker is
  launched, no slot is given, a remote spawn is refused, and a consult that would start a worker is refused.
- Without the hold, a worker started in the 15 s drain is orphaned by the exit, half-way through whatever it
  began.

**exec resolves at its timeout for every caller. Accepted.**
- Before, a held pipe could keep a call open past every deadline, and an upgrade could hang with no end.
- A caller now gets `code: null` and `timedOut`. Every caller already treats `code !== 0` as a failure.
- What outlives the kill is m2.

**A take_slot queued in the drain is lost untold. Accepted.**
- In `when_idle`, the drain starts only when no worker is active. A slot request in it would come from a worker
  started after the switch, and the hold prevents that.
- In `now`, the running workers are orphaned by the exit anyway. Their slot waits go with them. The next process
  reports them (orphaned, the restart notice; a v2 worker's spawner gets `exit`).
- An interactive agent's `take_slot` over MCP loses its connection at the exit, so its caller sees an error.
- A refusal at `acquire` while paused would be clearer, but it isn't needed. No finding.

**A board join can finish with no worker. Accepted; recorded in the ADR, as I advised (c_81760beb).**
- The second `refuseWhileRestarting` (`supervisor.ts:768`) runs after `session_join`. So the board has a join for a
  worker id that never runs.
- This isn't new. A supervisor crash between the join and `spawn()` leaves the same thing.
- What the board does with it:
  - the session has a member with no run;
  - the retry after `ready` joins again as a new worker id;
  - the session is closed at its boundary as usual.
- Starting the worker under the exit would be worse: it is killed within 15 s and comes back orphaned.

**Verify's budget.** `checked` gives each call what is left of the 75 s (`upgrade.ts:233-238`). So a fetch can
now take up to 75 s, where ruling 9 said 60 s. That is fine: the whole verify ends inside the requester's 90 s, with
room for the reply's trip. Recorded in the ADR.

## 4. rc.45: install and rollback order

rc.45 changes nothing on the wire:
- `packages/protocol` is unchanged in the range;
- the only new reply is the spawn refusal's `error` text, in the existing shape.

The database change is new values in the TEXT column `upgrades.stage`, with no column and no migration.

**Against rc.44, either order, both ways.**
- **rc.44 to rc.45 by `upgrade`.** rc.44 writes `restarting` at the switch. rc.45's `upgradesOpen` includes
  `restarting`, so it says `ready`.
- **rc.45 to rc.44 by `upgrade`.** rc.45 writes `installing`, then `waiting`, then `restarting`. rc.44 reads its
  `restarting` row and says `ready`.
- **A rollback by hand.** See §3, BOB-93.
- **Across laptops.** No message changes meaning.

**Against rc.41 (ubu1 until A-2).** rc.45 stands to rc.41 exactly as rc.44 does. The rc.43 rules still apply below
rc.43:
- **on install, the requester goes first;**
- **on rollback, the target goes back first.**

A-2 may install rc.44 or rc.45 directly.

So **rc.45 adds no order rule.**
