## 1. M1 is closed

- **The gate.** `ask()` refuses until `resume()` has run (`upgrade.ts:389`). `resume()` sets `resumed` first
  (`:425`). It is synchronous, so no ask can get in while it reads the rows.
  - `start()` calls `resume()` on every path that gets past registration (`supervisor.ts:634`). So the gate always
    opens.
  - If registration throws, `start()` fails and the process ends. A gate that stays shut there costs nothing.
  - The check comes after `releases.missing()` and the tag check, so a laptop with no `upgrade:` section gives the
    same answer as before.
- **Rows end once.** `moveUpgrade` and `endUpgrade` update only a row at `installing`, `waiting` or `restarting`
  (`store.ts:134`, `:653`, `:672`). They say whether the row changed. An ended row is never reopened, and its first
  end stands. That was the second half of M1.
- **An upgrade whose row was ended stops.** `run()`, `switchAndExit()` and `fail()` check that return value. If
  the row was ended, `dropped()` runs (`upgrade.ts:460`): it frees `current`, logs a warning, sends no event, and
  doesn't switch.
  - With the gate in place, nothing in the shipped paths ends another upgrade's row: `resume()` runs before any
    ask. So `dropped()` is a backstop, not a path. That is the right shape for it.
- **Double switch.** `switchAndExit()` now moves the row before it sets `u.state = "restarting"`. Both happen in
  the same synchronous step, before any await. A second `poke()` still sees `restarting` and returns
  (`upgrade.ts:416`).
- **Tests.** They cover the ACs:
  - "an upgrade asked during start() ..." holds the roles' registration, so `start()` is caught short of
    `resume()`. It checks the refusal, then that there was no event, no row, no build or discard, and no exit.
    Then it asks again and checks that the upgrade runs (AC 1, AC 3).
  - The store test covers AC 2.
  - "ended under it" checks the backstop.
- **AC 4.** packages/protocol and the config schema are untouched.

## 2. Departures

1. **`ask()` refuses until `resume()` has run, instead of moving `resume()` before registration. Accepted.**
   Moving `resume()` earlier would have needed two more changes:
   - `this.laptop`, which the notices use, is set only by the supervisor's own registration;
   - `sendRemote()` flushes the outbox without checking `registered`.

   The gate is one line, and the window it closes is a few seconds. The refusal reason is new text in the existing
   refusal shape. It is not a wire change.
2. **An ask in the start window is refused, not run. Accepted.** The broker delivers the messages it queued for an
   offline supervisor at that supervisor's registration, which falls in this window. So an ask sent while the
   target was down is always refused.
   - That is the right outcome. A self-upgrade shouldn't run from a stale queue without anyone watching.
   - The requester gets the refusal as its reply, and asks again once the target is `ready`.
   - If the requester's tool had stopped waiting by then, the late reply goes the way any late remote reply goes.
     That is ADR 0007; nothing new here.
3. **`run()` moves the row to `waiting` before it emits `installed`. Accepted, and better than before.** Both happen
   in one synchronous step.
   - If the process dies around that point, the row is now at `waiting`. `resume()` then says "restarted before the
     switch; <tag> stays installed", which is true.
   - With the old order, the row was still at `installing`, and `resume()` said "restarted while installing" about
     a build that had finished.
4. **A dropped upgrade says nothing more. Accepted.** Whatever ended the row already told the requester (today
   that can only be `resume()`). A second event would contradict it. The warning in the log is enough for a path
   the gate makes unreachable.

**A note, not a finding.** Before this change, `sendRemote()` could already flush the outbox before `registered`.
The cause is any push answered in the start window, such as this refusal. Then the start's queued items go out
before the roles have registered. Those are the orphans' `exit` events and the `remote:restarted` replies
(`supervisor.ts:591`, `:611`, whose comments say "flushed once registered").
- The supervisor's own name is registered by then, so the broker takes them. Nothing goes wrong.
- The comments are slightly off. Fix them next time the file is touched; no item needed.

## 3. ADR 0008

"As built, build D" adds what this build adds to §4 and "As built, build C" 4:
- asks are refused until the start has read the open rows;
- a row ends once;
- an upgrade whose row was ended stops without a word.

## 4. rc.45: no new order rule

rc.45 is everything on v2 since rc.44: build C (BOB-91..95) and build D (BOB-105).
- **Wire.** Unchanged. The new refusals (the drain, the start window) are reasons in the existing refusal shape. A
  requester on rc.43 or rc.44 shows them as it shows any refusal. A target below rc.45 never sends them.
- **Schema.** No migration. The new stages are text in an existing TEXT column (build C).
  - On rollback from rc.45 to rc.44, rc.44 leaves `installing` and `waiting` rows unread. Accepted in review C.
  - On going forward again, rc.45's `resume()` fails those stale rows once, and the requester hears one stale
    `failed`. That is the documented cost, not a rule.
  - BOB-105 changes no schema.
- **Order.** The rules in `rc44-notes.md` stand as they are:
  - below rc.43, install on the requester (mbp-1) first;
  - roll back the target first.

  rc.44 and rc.45 work in either order. mbp-1 is the only laptop with an `upgrade:` section (poe, A-2), and it gets
  rc.45 by hand. ubu1 follows A-2's runbook.
